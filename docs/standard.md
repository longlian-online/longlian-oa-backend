# 项目规范

## 命名
对象、方法、文件等命名，可以写的详细，可读性优先

## 注释
1. 不在没有理由的前提下移除注释

## 最小实现决策梯

处理需求前，先完整理解需求与受影响代码路径；然后按顺序停在第一个满足条件的层级：

1. 需求是否真的需要新增实现？不需要则明确说明并不实现。
2. 项目中是否已有可复用的能力、模式或基础设施？优先复用。
3. JDK / Spring / MyBatis Plus 等已使用的标准能力是否已经覆盖？优先使用。
4. 运行平台或浏览器原生能力是否覆盖？优先使用。
5. 已安装依赖是否覆盖？优先使用，不新增依赖。
6. 是否能以直接、清晰的一小段代码实现？
7. 仅在上述方式都不成立时，新增最小且完整的实现。

## Controller
1. 只做 DTO 的校验，BO 组装和 VO 的返回
2. 用户会话信息应该在 Controller 层取出并传入Service（对应 Service #2）
3. 接口按端别分开。用户端 Controller 不暴露、不转发组织管理端或平台管理端接口；组织管理端 Controller 不暴露、不转发平台管理端接口。用户端需要同类数据时，在用户端增加独立接口，只返回该端需要的字段，不复用管理端入口。调用方拥有更高角色，或服务端会拒绝越权，都不能代替这一区分。

## Service 

1. Service 层入参和出参须使用 BO 类，入参：XXXXParamsBO,出参：XXXXResultBO
2. Service 层方法应保持环境无关性。凡涉及用户会话信息（如 userId、orgId），应通过方法参数显式传递，严禁在 Service 内部直接访问 ThreadLocal 或 Session 上下文。此举旨在确保业务逻辑在 Controller、定时任务 (Cron)、消息处理 (MQ) 及单元测试 等多场景下的高度可复用性。
3. 以 MariaDB 作为唯一可靠数据源，Redis 仅做性能缓存加速，查询时优先走 Redis，一旦缓存查询异常、超时或宕机则自动降级直查 MariaDB，保证业务不受缓存故障影响。
4. 依赖事务提交后执行的缓存失效、通知发送等操作，调用链已明确保证事务同步时应直接注册 `afterCommit` 回调；禁止增加“无事务则立即执行”的兜底分支。缺少事务属于调用约束被破坏，应快速失败，避免产生与正常路径不同的提交、回滚语义。
5. 仅当组件的明确职责包含“既可加入现有事务，也可独立调用”时，才允许处理无事务场景；此时必须显式建立事务并测试两种调用路径。
6. 复用的数据库行锁方法必须使用 `Propagation.MANDATORY` 参与调用方事务，锁覆盖后续业务写入直到提交或回滚；禁止用独立事务提前释放锁。多行加锁先去重，使用主键排序的批量查询，空集合不执行锁查询；SQL 排序不保证数据库获取锁的顺序，仍需核查执行计划及其他写入路径的锁顺序。
7. Service 只负责本业务领域，可以编排其他 Service，不接管其他模块的数据操作和业务规则。
8. 需要其他模块的数据或规则时，调用该模块的 Service。尚未提供所需能力时，在归属模块增加表达业务意图的方法，不在调用方注入对方 Mapper 并自行实现。不为暴露底层 SQL 而增加没有业务含义的方法。
9. Service 只直接使用本领域的 Mapper。边界按数据和业务规则的归属判断，不以 Mapper 的包路径为准。确需跨模块使用 Mapper 时说明原因，并评估封装、耦合和后续维护成本。
10. 校验、状态流转和关联数据处理由所属模块负责。调用方不复制或重新组织对方已有规则；多处复用的能力由所属模块统一提供。
11. 跨模块流程中，调用方负责编排、状态跟踪和结果处理，各模块负责自己的数据和规则。按实际需要处理事务边界、幂等、异常和失败补偿。不为消除 Mapper 依赖引入 Service 循环依赖。

## Mapper
1. 数据库操作通过 Mapper 方法执行，优先复用 MyBatis Plus 的 `BaseMapper` 能力。
2. 查询 SQL 优先在 Java 代码中使用 `LambdaQueryWrapper` 构建，通过实体方法引用指定字段，保证类型安全；常规筛选、排序、分页、计数等查询不得另写 SQL 注解或 XML。
3. 仅当 `LambdaQueryWrapper` 无法清晰表达所需 SQL，或有明确的性能需求时，才允许在 Mapper 中使用 SQL 注解或 XML，例如复杂多表关联、窗口函数或数据库特有语法。不得为绕过此规范而改用字符串拼接、`apply` 或 `last` 堆砌复杂 SQL。
4. 使用 SQL 注解或 XML 时，应在对应 Mapper 方法或 SQL 附近说明不能使用 `LambdaQueryWrapper` 的原因；参数必须使用绑定参数（如 `#{param}`），禁止拼接外部输入或使用 `${}` 直接替换外部输入。

## 数据库变更

1. 数据库使用 Atlas 声明式管理，`db/schema.sql` 是数据库结构的唯一真实来源。
2. 修改数据库结构时，直接修改 `db/schema.sql` 中对应的现有表定义，使其表达目标状态。
3. 禁止维护第二份目标结构或版本式结构迁移链。历史数据转换使用 `db/data-migrations/*.sql`，统一在 Atlas 结构同步后执行，并按文件名记录成功状态；数据文件不编写 DDL，表结构只维护在 `schema.sql` 中。
4. 开发环境使用 `./db/migrate.sh dev plan` 预览变更，再使用 `./db/migrate.sh dev apply` 同步数据库；生产环境必须先审核 `./db/migrate.sh prod plan` 的结果。
5. 所有环境均不自动删除字段，生产环境还保护其他已有对象的删除。旧字段保留供数据转换使用，清理须作为单独、经审核的运维操作执行。
6. 数据迁移文件名是全局唯一、区分大小写的执行标识。已成功执行的文件不得修改或改名，后续修正必须新增文件。文件不得自行提交事务或写执行记录，数据修改与成功记录由通用执行器一起提交。
7. 禁止使用外键约束，`schema.sql` 不定义 `FOREIGN KEY`；引用完整性由应用层维护：写入前校验被引用对象存在且状态合法，删除被引用对象时由业务代码决定拒绝还是级联处理，并发冲突以唯一索引兜底。

## 定时任务
1. 任务须实现 `ScheduledTask` 接口，通过 `getDefinition()` 返回任务定义
2. 任务定义通过 `ScheduledTaskDefinition` 构造方法创建，包含：taskName（唯一标识）、description（必填的任务描述，建议用中文写清任务用途）、cronExpression（Spring 6 字段格式；仅手动触发时可为 null）、enabled；构造方法校验字段，调度引擎校验任务标识唯一性
3. 所有任务执行记录自动写入 `scheduled_task_log` 表，可通过 `admin/ScheduledTaskController` 手动触发任务
4. 定时任务应保持环境无关性 —— 业务逻辑中涉及用户会话信息（如 userId、orgId），须通过 `execute(LocalDateTime executeTime)` 方法参数传递，禁止在任务内部直接访问 ThreadLocal
5. 明确禁止在任务中获取当前时间，必须使用入参传递的 executeTime 作为当前时间(事实上定时任务传递的 executeTime 也确实是当前时间)，因为手动调用接口时可以传递任意的执行时间
6. 定时任务尽量保证幂等
